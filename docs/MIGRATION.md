# Миграция Mongo ↔ SQLite

Шаг 8 фазы 2. Консольный инструмент переносит доски, элементы, участников и
роли, приглашения и устройства между MongoDB сервера и локальной базой SQLite.
Обе стороны используют один снимок данных, поэтому направления симметричны.

## Запуск

Собрать сервер (в толстом jar уже есть классы миграции):

```bash
JAVA_HOME=/usr/lib/jvm/openjdk21 ./mvnw -B -f java-collab/server/pom.xml package
```

Затем:

```bash
# Mongo → SQLite
java -cp java-collab/server/target/canvas-collab-server-1.0.0.jar \
  org.example.canvasproject.migration.MigrationCli mongo sqlite \
  --dir ~/.local/share/canvasproject

# SQLite → Mongo
java -cp java-collab/server/target/canvas-collab-server-1.0.0.jar \
  org.example.canvasproject.migration.MigrationCli sqlite mongo \
  --dir ~/.local/share/canvasproject
```

Параметры:

| Параметр | Значение |
|---|---|
| `--dir <каталог>` | каталог локальных данных SQLite; по умолчанию `XDG_DATA_HOME/canvasproject` или `~/.local/share/canvasproject` |
| `--db <файл>` | явный файл SQLite; по умолчанию `<каталог>/slate.db` |
| `MONGO_URI` | по умолчанию `mongodb://localhost:27017` |
| `MONGO_DB` | по умолчанию `canvas_collab` |

Коды выхода: `0` — перенос и сверка успешны; `1` — ошибка или расхождение;
`2` — неверные аргументы.

## Что переносится

- доски: id, имя, владелец, размеры, время создания и изменения;
- участники и роли (`owner`/`editor`/`viewer`);
- элементы: id, тип, JSON `data`, автор, `updatedAt`, порядок;
- приглашения: код, доска, автор, роль, срок, лимит и число использований;
- устройства/пользователи: id, имя, email, хеш пароля, хеш ключа устройства,
  цвет, аватар, время создания.

Файлы изображений (`AssetStore`) инструмент не копирует: он переносит только
записи хранилища. Если изображения уже вынесены из base64 в файлы, каталог
`assets` нужно перенести отдельно.

## Резервная копия и манифест

До записи:

- для SQLite-назначения делается `PRAGMA wal_checkpoint(TRUNCATE)` и копия
  файла базы в `<каталог>/backups/slate-<время>.db`;
- для Mongo-назначения коллекции `users`, `canvases`, `invite_codes`
  выгружаются в `<каталог>/backups/mongo-<время>.json` (Extended JSON).

Сессии (`device_tokens`) не выгружаются: это не данные пользователя, а
временные токены.

Манифест `<каталог>/migration-manifest.json` пишется дважды: со статусом
`running` перед записью и итоговый (`ok`/`failed`). В нём — направление,
пути копий, счётчики до/после, число проверенных записей, предупреждения и
список расхождений. Коды приглашений, ключи устройств и пароли в манифест не
попадают.

## Идемпотентность и прерванный запуск

Запись — upsert по устойчивым идентификаторам:

- доски и устройства обновляются по id;
- элементы и участники доски зеркалятся: набор заменяется целиком, лишние
  элементы удаляются, недостающие добавляются;
- приглашения обновляются по коду.

Поэтому повторный запуск не создаёт дублей, а прерванный переноса
дозавершается: уже записанное обновляется, оставшееся дописывается. Изменения
источника (например, правка `data` элемента) переносятся следующим запуском.

Лишние записи, которые уже были в назначении и отсутствуют в источнике, не
удаляются — они попадают в общие счётчики и не считаются ошибкой.

## Идентификаторы

- **Mongo → SQLite**: все id сохраняются как есть (ObjectId становится
  24-символьной строкой).
- **SQLite → Mongo**: id, уже являющийся 24-символьным hex, сохраняется. UUID
  локальных досок и устройств превращается в ObjectId детерминированно:
  SHA-256 от `пространство:исходный id`. Повторный запуск получает тот же
  ObjectId. Ссылки на пользователей (`ownerId`, `memberIds`, роли, `addedBy`,
  `createdBy`) переписываются на новые id; приглашения получают ObjectId от
  кода и ссылаются на новую доску.

## Сверка

После записи инструмент заново читает назначение и проверяет:

- наличие каждой доски и совпадение имени, владельца, размеров и времени;
- набор участников и их роли;
- число элементов доски и содержимое каждого элемента (JSON сравнивается без
  учёта порядка ключей и типа числа);
- каждое приглашение: доска, роль, срок, лимит, число использований;
- каждое устройство: имя, email, хеши, цвет, аватар, время создания.

При любом расхождении — сообщения в отчёте, статус `failed` в манифесте и код
выхода `1`.

## Ограничения

- Mongo не хранил `createdAt` приглашений; инструмент пишет это поле при
  переносе, у старых документов оно равно `0`.
- Если в назначении тот же хеш ключа устройства или email принадлежит другому
  id, перенос останавливается с понятной ошибкой: автоматическое слияние
  аккаунтов не выполняется.
- Инструмент рассчитан на согласованный запуск, когда сервер не пишет в базу;
  блокировок на время переноса нет.
- Mongo-выгрузка читает коллекции в память; для очень больших баз её нужно
  делать по частям (в текущем объёме Slate это не требуется).

## Проверка

```bash
# юнит-тесты миграции без Mongo
JAVA_HOME=/usr/lib/jvm/openjdk21 \
  ./mvnw -B -f java-collab/server/pom.xml \
  -Dtest='MigrationRunnerTest,MongoMigrationStoreTest,MigrationCliTest' test

# интеграционные сценарии в обе стороны (нужна тестовая Mongo)
SLATE_INTEGRATION_TESTS=1 MONGO_DB=canvas_collab_test \
MONGO_URI=mongodb://localhost:27017 \
JAVA_HOME=/usr/lib/jvm/openjdk21 \
  ./mvnw -B -f java-collab/server/pom.xml \
  -Dtest='MongoSqliteMigrationIntegrationTest' test
```

Интеграционный тест пропускается, если `SLATE_INTEGRATION_TESTS != 1`,
`MONGO_DB` не содержит `test` или Mongo недоступна.
