# Решения (DECISIONS)

Формат: дата — решение — почему — последствия. Необратимые решения требуют
подтверждения владельца проекта и здесь не принимаются самовольно.

## D-001. Фаза 0 без изменения поведения (2026-11-22)

**Решение.** До завершения фазы 0 не менять пользовательское поведение и
визуальный стиль. Добавляются только документация, тесты, CI и минимальные
технические правки, без которых тесты невозможны.

**Почему.** Нужен страховочный baseline: аудит и регрессионные тесты до
рефакторинга.

**Последствия.** Найденные дефекты фиксируются в `AUDIT.md`, но исправляются в
фазе 1.

## D-002. Два независимых Maven-проекта (2026-11-22)

**Решение.** Клиент (`pom.xml` в корне, Java 17) и сервер
(`java-collab/server/pom.xml`, Java 21) собираются отдельно; агрегаторный POM не
вводится на фазе 0.

**Почему.** Это текущая структура; агрегация смешала бы версии Java и сломала бы
существующие скрипты.

**Последствия.** CI собирает оба проекта отдельными job'ами; `verify` в корне не
проверяет сервер.

## D-003. Интеграционные тесты — только на тестовой БД (2026-11-22)

**Решение.** Тесты протокола запускаются при `SLATE_INTEGRATION_TESTS=1` и
только если `MONGO_DB` содержит `test`; перед прогоном база очищается. По
умолчанию тесты пропускаются.

**Почему.** Обычная сборка не должна требовать MongoDB, а случайный запуск не
должен уничтожить рабочие доски.

**Последствия.** Локально и в CI интеграционные тесты включаются явно; на
Windows/macOS они пропускаются.

## D-004. Локализация — постепенно, новые строки только через ресурсы (2026-11-22)

**Решение.** Существующие строки в коде — зафиксированный технический долг. Все
новые пользовательские строки добавляются в `messages_ru.properties` /
`messages_en.properties` (структура будет введена в фазе 1 вместе с диалогами).

**Почему.** Полная локализация в фазе 0 изменила бы поведение и раздула бы
дифф; правило «новые строки — через ресурсы» соблюдается сразу.

**Последствия.** Полное вынесение строк — отдельная задача фазы 1/6.

## D-005. Версии Java и CI (2026-11-22)

**Решение.** Клиент — JDK 17, сервер — JDK 21. CI: клиент на Ubuntu/Windows/
macOS с JDK 17, сервер с MongoDB на Ubuntu с JDK 21. Системная Java 11 не
используется.

**Почему.** Соответствует `pom.xml`; JavaFX 17 не требует Java 21, сервер уже
использует Java 21.

**Последствия.** Локально `JAVA_HOME` обязателен; это записано в `AGENTS.md`.

## D-006. Хранилище: SQLite внутри, `.slate` для обмена, MongoDB опционально (2026-11-22, подтверждено владельцем)

**Решение.** Основной движок хранения — встроенный SQLite: один файл, без
установки, подходит для solo-режима и LAN-хоста. `.slate` — открытый формат
обмена и резервных копий (zip: `board.json` + `assets/`), не основное хранилище.
MongoDB остаётся опциональным адаптером для существующих серверов; миграция
Mongo ↔ SQLite обязательна и тестируется.

**Почему.** Local-first и «данные — ваши файлы» без внешней службы; при этом
нельзя терять уже развёрнутые Mongo-инсталляции.

**Последствия.** Фаза 2 вводит интерфейсы репозиториев, `SqliteStorage` по
умолчанию, `MongoStorage` как адаптер, команды импорта/экспорта `.slate` и
миграцию. Формат `.slate` версионируется и описывается в `docs/FORMAT.md`.

## D-007. Лицензия: MIT (2026-11-22, подтверждено владельцем)

**Решение.** Проект остаётся под MIT. AGPL-3.0 не применяется.

**Почему.** Максимальная свобода использования и совместимость с экосистемой;
решение владельца после обсуждения альтернативы AGPL.

**Последствия.** `LICENSE` и README не меняются; вклады принимаются на условиях
MIT.

## D-008. Никакой телеметрии по умолчанию (2026-11-22)

**Решение.** Приложение не отправляет аналитику и не требует сетевого доступа
для solo-режима.

**Почему.** Local-first и приватность — часть целевой картины.

**Последствия.** Любая будущая телеметрия — только opt-in и отдельным решением.

## D-009. Порядок фазы 1 (2026-11-22, подтверждено владельцем)

**Решение.** Работы идут строго в порядке: (а) потеря данных и безопасность;
(б) минимальное восстановление сессии, индикатор связи, единый обработчик;
(в) Undo/Redo на сервере в минимальном объёме; (г) права наблюдателя и показ
ошибок; (д) синхронизация размера холста; (е) диалоги, локализация, окно, сетка,
перо, README, мёртвый код.

**Почему.** Сначала исключаем потерю данных и обход прав, затем восстанавливаем
связь, и только потом занимаемся UX.

**Последствия.** Для каждого дефекта сначала пишется падающий тест, затем фикс.

## D-010. CI на GitHub пока не проверен (2026-11-22)

**Решение.** Workflow `.github/workflows/ci.yml` остаётся в репозитории, но
реальный прогон в GitHub Actions не выполнен: `gh` не установлен, токена нет,
SSH-ключ не авторизован, remote отсутствует.

**Почему.** Создание репозитория и публикация требуют доступа к аккаунту,
которого у агента нет.

**Последствия.** Локальные команды `clean verify` зелёные; статус CI считается
непроверенным до первого push в GitHub.

## D-011. Общий слой `slate-core` без переезда модулей (2026-11-25)

**Решение.** Интерфейсы хранилища, DTO, `AssetStore`, формат `.slate` и
серверные команды живут в `slate-core/src/main/java`. Клиент и сервер
подключают этот каталог через `build-helper-maven-plugin`, а не через
Maven-зависимость. Тесты контрактов лежат в `slate-core/src/test/java` и
компилируются в оба проекта.

**Почему.** Сервер — отдельный Maven-проект, а встроенному серверу нужен тот
же код, что и сетевому. Модульная перестройка сломала бы скрипты, CI и пути;
компиляция общего исходника даёт один источник истины без `install`.

**Последствия.** `slate-core` не зависит от JavaFX, Mongo и WebSocket — только
`org.json` и JDK. Mongo-адаптеры остаются в сервере, SQLite — в клиенте.

## D-012. Контрактные тесты хранилища (2026-11-25)

**Решение.** `StorageContract` — один абстрактный набор на 11 сценариев
(доски, роли, каскад, порядок и upsert элементов, атомарность пакетов,
приглашения, устройства). Наследники: `SqliteStorageContractTest` (всегда) и
`MongoStorageContractTest` (при `SLATE_INTEGRATION_TESTS=1` и `MONGO_DB` с
`test`). Пакетные `updateMany`/`deleteMany` валидируют весь список до записи и
применяются одной транзакцией (SQLite) или одним атомарным обновлением
документа (Mongo).

**Почему.** Поведение хранилищ должно совпадать, иначе встроенный и сетевой
режимы разойдутся.

**Последствия.** Любой новый адаптер обязан пройти `StorageContract`; для
Mongo индексы пересоздаются при открытии хранилища (`ensureIndexes`), потому
что тестовая база может быть удалена между тестами.

## D-013. Импорт `.slate`, снимки и первый запуск (2026-11-25)

**Решение.** Импорт `.slate` всегда создаёт новую локальную доску; id и
времена из файла не используются. Архив читается и проверяется целиком до
записи в SQLite/`AssetStore`; допустимы только `board.json` и
`assets/<sha256>`, лимиты — 512 файлов, 64 МиБ JSON, 16 МиБ на ассет, 256 МиБ
суммарно. Ошибки формата несут ключ локализации (`SlateFileException`), а не
текст. Снимки — полный JSON доски (тот же `board.json`) в таблице
`board_snapshots` того же SQLite; хранятся последние 10, более старые
удаляются одной транзакцией. Снимок пишется перед крупной потерей элементов
(было ≥ 4, остаётся меньше половины), перед восстановлением снимка и после
импорта, а также не чаще раза в 5 минут при автосохранении. Если основная запись не
читается, `find` возвращает последний снимок; если основная запись пуста, а
снимок новее её `updated_at` и содержит элементы — содержимое поднимается из
снимка (очищенная пользователем доска не восстанавливается, потому что её
`updated_at` новее снимка).

**Почему.** Нельзя терять данные при сбое и нельзя давать архиву писать вне
каталога или раздувать память. Отдельная таблица снимков через
`CREATE TABLE IF NOT EXISTS` не меняет `PRAGMA user_version` и не ломает
существующие базы.

**Последствия.** Схема SQLite получает две служебные таблицы
(`board_snapshots`, `app_flags`) при первом открытии; `user_version` остаётся
2. Доска «Без названия» создаётся один раз при первом запуске с пустым
хранилищем, флаг `welcome-board-created` не даёт создавать её снова после
удаления. Решение о ручном выборе снимка в интерфейсе не принималось: сейчас
снимки доступны через `LocalBoardService.snapshots/restoreSnapshot`.

## D-014. Инструмент «Выделение», рамка и групповые операции (2026-11-25)

**Решение.** «Выделение» — режим по умолчанию; кнопка с иконкой курсора в доке,
клавиша `V`, стрелка вместо кисти. Выделение — локальное состояние клиента и по
сети не передаётся. Наблюдатель может выделять и смотреть свойства, но ручки,
перемещение, стиль и удаление у него отключены.

Рамка работает в координатах холста (`sceneToLocal`), поэтому одинаково ведёт
себя при масштабе 0.1–8 и после панорамирования. Протягивание начинается после
порога 3.5 экранных пикселя; пустое место рисует рамку, нажатие на выбранный
элемент — перемещает группу. Слева направо рамка выделяет целиком попавшие
элементы (сплошная граница), справа налево — пересечённые (пунктир). `Shift`
добавляет/убирает, `Ctrl` переключает, без модификаторов выделение заменяется.
`Ctrl+A` — все, `Esc` — снять, `Tab`/`Shift+Tab` — следующий/предыдущий.

Попадание в рамку: фигуры, текст, картинки и стикеры проверяются по
`getSelectBounds()`; линия — сначала по bounding box, затем по точкам и
отрезкам. В режиме «целиком» все точки линии должны быть внутри рамки, в режиме
«касание» достаточно точки или пересечения отрезка со стороной рамки. Толщина
обводки в геометрию не входит — иначе тонкая линия «не попадала» бы в рамку.

Поиск кандидатов идёт через равномерную сетку 256 px (`SpatialIndex`), а не
перебором всех элементов: на 5000 элементов запрос рамки смотрит только
пересечённые ячейки, порядок результатов восстанавливается по модели (z-порядок).
Индекс обновляется при добавлении/удалении, в конце жеста и при удалённых
изменениях; промежуточные движения пересчитывают только сдвинутые элементы.

Одно групповое действие — одна команда истории. `GroupChangeCommand` хранит для
каждого элемента снимок «до»/«после» и прозрачность узла (её нет в
`ElementMemento`), `DeleteElementsCommand` — прежние индексы для точного Undo в
z-порядке, `AddElementsCommand` — вставку/дублирование. Перетаскивание считает
смещение от начала жеста и не накапливает ошибку; при включённой сетке шаг 40 px
(Shift — 10 шагов при перемещении с клавиатуры). Масштабирование группы идёт от
общих границ: элемент переносится в целевую точку и получает новый размер,
поэтому общий контур не «плывёт».

Изменения отправляются пакетом: `UPDATE_ELEMENTS`/`DELETE_ELEMENTS`, сервер
применяет их одной транзакцией и рассылает `ELEMENTS_UPDATED`/`ELEMENTS_DELETED`
всем, кроме инициатора. Промежуточные позиции при перетаскивании уходят не чаще
45 мс, финальная — всегда. Если элемент исчез или изменился на сервере, он тихо
выпадает из выделения, а групповой жест пропускает исчезнувшие элементы.

Стили группы: цвет — фигуры, линии и текст; толщина — только линии; прозрачность
— все типы (через `Node.opacity`, альфа обводки линии). Свойства, которых нет у
всех выбранных типов, в панели скрываются; различающиеся значения помечаются
«разные». Стикер не участвует в смене цвета: публичного сеттера нет, а менять
его файл в этой задаче нельзя.

**Почему.** Прямой перебор элементов на каждое движение мыши не держит 5000+
элементов, а отдельные команды на элемент засоряют историю и рассылают N
сообщений. Локальное выделение не создаёт конфликтов между участниками.

**Последствия.** `SelectionManager` стал групповым (сохранив одиночный
`SelectionOverlay`), добавлены `GroupSelectionOverlay`, `MarqueeOverlay`,
`SelectionGeometry`, `SpatialIndex` и три команды. `BoardModel` получил
`insert`, `queryIn`, `findAt`, `refreshSpatialIndex`. Старые доски и ключи
устройств не затрагиваются: формат элементов не менялся, добавлено только
необязательное поле `nodeOpacity` в `data`.

## D-015. Solo-режим идёт через встроенный сервер команд, а не отдельный процесс (2026-11-25)

Решение: локальная доска обслуживается `LocalServer` в том же JVM, а не
отдельным HTTP/WebSocket-процессом. Клиент общается с ним через
`Transport` (`InProcessTransport`), формат сообщений, проверки прав и
пакетные операции совпадают с сетевым сервером.

**Почему.** Это исключает вторую реализацию правил («локально можно всё») и
позволяет одним набором тестов проверить и solo, и сеть. Отдельный процесс
потребовал бы порт, авторизацию и ещё один жизненный цикл без пользы для
одного участника.

**Последствия.** `CollaborationClient` получил локальный транспорт и
использует его, пока он открыт; при возврате к списку досок транспорт
снимается. Подтверждения собственных изменений (`ELEMENT_ADDED` и т. п.)
локальный транспорт не доставляет — как и WebSocket-сервер, иначе элемент
применился бы дважды. Формат `device.json` и существующие доски не меняются.
